# AlertLens — demo

## 2-minute spoken explanation

"AlertLens is a SOC triage dashboard. The problem is alert fatigue: analysts get thousands of alerts, most of them the same detection firing over and over, or several detections that are really one attack. So AlertLens does three things. First, it deduplicates — the same rule on the same host and IPs inside five minutes is one alert, and the repeats are linked, never deleted, so suppression is auditable. Second, it correlates what is left into incidents by host, and scores the *incident* — severity, how critical the asset is, and a machine-learning probability pooled with noisy-OR, so one strongly malicious alert surfaces even among benign ones — instead of ranking single alerts. And third, it enforces a false-negative budget: the suppression threshold is calibrated so at least 95% of malicious incidents still surface, and we report the alert reduction only after that constraint is met — if recall falls short, the dashboard says 'target not met' instead of showing a reduction number. Each incident gets a one-screen evidence package — who, what, when, why, the MITRE techniques, and a next action — and analysts mark true or false positive, which feeds a retrain script. In the demo, 152 seeded alerts collapse to 8 incidents (8 surfaced, 0 suppressed), headline 94.74%, recall 1.0 — synthetic data, so treat the numbers as a pipeline check, not production performance. (A work copy with a UNSW-NB15-trained model scores the same demo set differently — 6 surfaced, 2 suppressed, headline "target not met", recall 0.75 — because the model and threshold differ; see RESULTS.md.) The real evaluation is a 5-seed incident-level test on 300 labelled scenarios per seed with overlapping flow distributions: recall 0.9419, precision 0.6451, reduction 70.02% — and the 0.95 recall target is not met in seeds 2 and 3, while mean pooling ties on recall and fails in seeds 0 and 3. On real UNSW-NB15 test flows the model scores recall 0.9486, precision 0.9334 — the target is not met there either, measured in the work-copy run."

## 5-step demo script

1. **Show the input.** Open `data/sample_alerts.csv`: point out the 40x PowerShell storm, the 25x registry storm, and the three attack chains (web-01 recon → PowerShell → exfiltration; db-01 credential dump → lateral movement; dc-01 privilege escalation → ransomware). Note the new `raw` column: every alert carries UNSW-NB15-style flow features (dur, sbytes, dbytes, rate, sttl, ct_srv_src) that the model scores on.
2. **Load it live.** Run `API_URL=http://localhost:8000 API_KEY=<key> python scripts/load_csv.py data/sample_alerts.csv` and read the output: 87 inserted, 65 duplicates.
3. **Dashboard.** Open the UI: the headline card shows 94.74% after-triage reduction, the dedup/correlation card shows 94.74%, and the surfaced/suppressed cards show 8 surfaced, 0 suppressed. The bar chart shows 152 raw alerts vs 8 incidents vs 8 surfaced incidents. Say the reduction number out loud — and say why it is shown at all: recall is 1.0, above the 0.95 target.
4. **Incident detail + suppression/reopen.** Open the top incident (Mimikatz Credential Dump on db-01, priority 0.92): read the evidence package — critical asset, MITRE T1003.001/T1021.002, the two-alert timeline — then mark it true positive and move it to `investigating`. Then demonstrate suppression: post one benign low-severity alert with benign flows (e.g. a single `Suspicious Registry Change` with `raw: {"dur": 0.5, "sbytes": 500, "dbytes": 300, "rate": 10, "sttl": 254, "ct_srv_src": 1}`) — it forms an incident below the threshold, so it is suppressed and hidden from the default queue. Tick "Show suppressed" in the Queue to reveal it with its "suppressed" badge, open it to see the banner with the suppression reason, and click "Reopen incident" to put it back in the queue as `new`. Nothing was deleted at any point.
5. **Prove the numbers.** Run `python benchmark.py` in the terminal and read the output: Part A (152 alerts → 8 incidents, 8 surfaced, headline 94.74%, recall 1.0, precision 0.5, dedup latency ~6 ms/alert, varies run to run), Part B, the 5-seed incident-level evaluation with the baseline table — AlertLens recall 0.9419 ± 0.0699, precision 0.6451, reduction 70.02% ± 5.68%, target not met in seeds 2 and 3; mean pooling ties on recall (0.9419) and beats it on precision (0.7256), failing in seeds 0 and 3; severity-only meets recall at precision 0.4937 — and Part C is NOT RUN in this build (no UNSW-NB15 file shipped); the work-copy Part C numbers are recall 0.9486, precision 0.9334, reduction 30.83%, target not met. Close by noting the synthetic-data limitation and the upper-bound caveat (generator and model share distributions in Part B).
