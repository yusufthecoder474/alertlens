# AlertLens — demo

## 2-minute spoken explanation

"AlertLens is a SOC triage dashboard. The problem is alert fatigue: analysts get thousands of alerts, most of them the same detection firing over and over, or several detections that are really one attack. So AlertLens does three things. First, it deduplicates — the same rule on the same host and IPs inside five minutes is one alert, and the repeats are linked, never deleted, so suppression is auditable. Second, it correlates what is left into incidents by host, and scores the *incident* — severity, how critical the asset is, and a machine-learning probability pooled with noisy-OR, so one strongly malicious alert surfaces even among benign ones — instead of ranking single alerts. And third, it enforces a false-negative budget: the suppression threshold is calibrated so at least 95% of malicious incidents still surface, and we report the alert reduction only after that constraint is met — if recall falls short, the dashboard says 'target not met' instead of showing a reduction number. Each incident gets a one-screen evidence package — who, what, when, why, the MITRE techniques, and a next action — and analysts mark true or false positive, which feeds a retrain script. In the demo, 152 seeded alerts collapse to 7 incidents, a 95.39% after-triage reduction, with recall of 1.0 on the seeded set — synthetic data, so treat the numbers as a pipeline check, not production performance. The real evaluation is a 5-seed incident-level test on 300 labelled scenarios per seed: recall 0.9935, precision 1.0, reduction 79.54% — and mean pooling, the old approach, fails the recall target in 3 of 5 seeds."

## 5-step demo script

1. **Show the input.** Open `data/sample_alerts.csv`: point out the 40x PowerShell storm, the 25x registry storm, and the three attack chains (web-01 recon → PowerShell → exfiltration; db-01 credential dump → lateral movement; dc-01 privilege escalation → ransomware). Note the new `raw` column: every alert carries UNSW-NB15-style flow features (dur, sbytes, dbytes, rate, sttl, ct_srv_src) that the model scores on.
2. **Load it live.** Run `API_URL=http://localhost:8000 API_KEY=<key> python scripts/load_csv.py data/sample_alerts.csv` and read the output: 88 inserted, 64 duplicates.
3. **Dashboard.** Open the UI: the headline card shows 95.39% after-triage reduction, the dedup/correlation card shows 95.39%, and the surfaced/suppressed cards show 7 surfaced, 0 suppressed. The bar chart shows 152 raw alerts vs 7 incidents vs 7 surfaced incidents. Say the reduction number out loud — and say why it is shown at all: recall is 1.0, above the 0.95 target.
4. **Incident detail + suppression/reopen.** Open the top incident (Privilege Escalation Attempt on dc-01, priority 0.95): read the evidence package — critical asset, MITRE T1068/T1486, the two-alert timeline — then mark it true positive and move it to `investigating`. Then demonstrate suppression: post one benign low-severity alert with benign flows (e.g. a single `Suspicious Registry Change` with `raw: {"dur": 0.5, "sbytes": 500, "dbytes": 300, "rate": 10, "sttl": 254, "ct_srv_src": 1}`) — it forms an incident below the threshold, so it is suppressed and hidden from the default queue. Tick "Show suppressed" in the Queue to reveal it with its "suppressed" badge, open it to see the banner with the suppression reason, and click "Reopen incident" to put it back in the queue as `new`. Nothing was deleted at any point.
5. **Prove the numbers.** Run `python benchmark.py` in the terminal and read the output: Part A (152 alerts → 7 incidents, 95.39% headline reduction, recall 1.0, precision 0.5714, dedup latency ~2 ms/alert) and Part B, the 5-seed incident-level evaluation with the baseline table — AlertLens recall 0.9935 ± 0.0144, precision 1.0000, reduction 79.54% ± 2.09%; mean pooling fails the 0.95 recall target in seeds 2, 3 and 4; severity-only meets recall at precision 0.4937. Close by noting the synthetic-data limitation and that the UNSW-NB15-derived evaluation is NOT RUN (no dataset file).
