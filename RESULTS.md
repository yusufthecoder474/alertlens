## How to read these numbers

- **Part A (demo pipeline, synthetic seeded set):** 152 alerts collapse to 7 incidents; 64 duplicates linked, never deleted. After-triage reduction (95.39%) equals the dedup/correlation reduction here because no incident was suppressed in the demo set (all 7 surfaced). Recall 1.0 means every labelled malicious incident surfaced; precision 0.5714 means 4 of the 7 surfaced incidents are malicious and 3 are benign noise groups — an honest consequence of synthetic data, listed as a limitation in the README. Dedup latency varies run to run (earlier run: 2.308 ms/alert; this run: 2.138 ms/alert); the number above is from this run only.
- **Part B (synthetic scenario set):** the real evaluation. Each seed generates 300 labelled scenarios (140 malicious) including hard cases — benign admin PowerShell storms, scheduled-backup bursts, low-severity first-stage attacks, multi-host chains — split 60/20/20 stratified by label; the flow model trains on 2,000 synthetic flows per seed; the threshold is calibrated on VAL incidents and evaluated on TEST incidents. AlertLens (noisy-OR pooling) meets the 0.95 recall target on test in all 5 seeds (mean recall 0.9935 ± 0.0144, precision 1.0000, after-triage reduction 79.54% ± 2.09%). Pooled test recall is 155/156 = 0.9936 with a 95% Wilson interval of [0.9646, 0.9989].
- **Baselines (synthetic scenario set):** mean pooling — the old pooling — fails the 0.95 recall target on test in 3 of 5 seeds (mean recall 0.9290 ± 0.0735), which is the direct evidence for the noisy-OR fix: averaging lets benign alerts dilute an attack. Severity-only meets recall (1.0000) but at precision 0.4937 and only 58.30% reduction — it surfaces roughly half the benign incidents too. AlertLens wins on recall (target met every seed) and precision (1.0000), at a small reduction cost vs mean pooling (79.54% vs 80.80% — mean pooling's higher reduction comes from suppressing attacks it should have surfaced).
