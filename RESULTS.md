# AlertLens — measured results

Generated by running `python benchmark.py` in the **extracted portable build**
(the zip contents, no `models/model.pkl`, no UNSW-NB15 data) on 2026-11-19.
Reproduce with: `python benchmark.py`

## Portable build vs work-copy evaluation

Two builds exist, and their numbers differ because the model differs:

- **Portable build (this zip).** Ships no trained model (`models/model.pkl`
  is excluded) and no UNSW-NB15 data. At first load the API trains a
  synthetic model in memory (`generate_synthetic_flows(2000, seed=42)`) and
  calibrates its own threshold on the matching synthetic validation split
  (80/20 stratified, `random_state=42`) — see `api/scoring.py::load_model`.
  It never reads `models/threshold.json`: that file belongs to the
  UNSW-trained model and is shipped only as a record of the work-copy
  calibration (source `unsw-nb15.csv`, threshold 0.6278); the fallback
  ignores it. Part A and Part B below are measured on this build.
  Part C is **NOT RUN** here — there is no dataset file to run it on.
- **Work-copy evaluation (optional).** In a copy where
  `data/unsw-nb15.csv` exists, `python scripts/train.py` trains a model on
  real UNSW-NB15 flows and writes `models/model.pkl` +
  `models/threshold.json` (threshold 0.6278 with the 6-feature
  severity-free model). That copy's Part A is 152 alerts → 8 incidents
  (6 surfaced, 2 suppressed), headline "target not met", recall 0.75,
  precision 0.5; its Part C is given in the separate section below,
  labelled "measured in the work-copy run". Those numbers are **not**
  the portable build's numbers and are never presented as such.

Fix pass 3.1 fixed a model/threshold mismatch in `load_model()`: the old
fallback trained a synthetic model but loaded the threshold from
`models/threshold.json`, pairing a synthetic-trained model with a
UNSW-calibrated threshold (0.6278). The fallback now trains **and**
calibrates its own threshold on a deterministic synthetic train/validation
split (seed 42) and never reads `threshold.json` in that path; three
regression tests cover it (`test_fallback_ignores_unsw_threshold_json`,
`test_fallback_works_without_any_threshold_file`,
`test_saved_model_uses_its_paired_threshold`). That is why Part A changed
from the work-copy run (6 surfaced, recall 0.75, threshold 0.6278) to the
portable run above (8 surfaced, recall 1.0, threshold 0.1539): the model
and the threshold are different, and the portable numbers are the ones
that belong to this build. Part B is identical in both builds (it trains
its own synthetic model per seed, so the saved model never enters it).

Fix pass 3 removed `severity_num` from the ML feature set (UNSW-NB15 has
no severity column; the old feature was all-NaN in UNSW training, which
is what made sklearn print `UserWarning: Skipping features without any
observed values: [6]`). The warning is fixed at its source — the feature
no longer exists — and a clean `python -W always benchmark.py` run now
prints nothing to stderr (verified: 0 lines, this run). Severity enters
only through the priority formula.

## How to read these numbers

- **Part A (demo pipeline, synthetic seeded set, portable build):** 152
  alerts collapse to 8 incidents through the real ingest pipeline; 65
  duplicates linked, never deleted. All 8 incidents surface at the
  fallback's self-calibrated threshold (0.1539): recall 1.0 (4 of 4
  labelled malicious incidents surfaced), precision 0.5 (4 of the 8
  surfaced incidents are malicious, 4 are benign noise groups — an honest
  consequence of synthetic data, listed as a limitation in the README).
  Dedup latency varies run to run; the number above is from this run only.
- **Part B (synthetic scenario set, harder generator):** the real
  evaluation. Each seed generates 300 labelled scenarios (140 malicious)
  including hard cases — benign admin PowerShell storms, scheduled-backup
  bursts, low-severity first-stage attacks, multi-host chains — split
  60/20/20 stratified by label; the flow model trains on 2,000 synthetic
  flows per seed; the threshold is calibrated on VAL incidents and
  evaluated on TEST incidents. The generator uses **overlapping** flow
  distributions (malicious `sttl` ~ N(90,45) vs benign ~ N(200,60);
  malicious `rate` 1–800 vs benign 0.1–400; ~15% of malicious scenarios
  use benign-like flows and ~10% of benign scenarios use malicious-like
  flows), and the generator and model share those distributions — so
  these numbers are an **upper bound** on what the same approach would do
  on truly unseen distributions, stated in the README. AlertLens
  (noisy-OR pooling) does **not** meet the 0.95 recall target: mean
  recall 0.9419 ± 0.0699, precision 0.6451 ± 0.0943, after-triage
  reduction 70.02% ± 5.68%; pooled test recall 147/156 = 0.9423 with a
  95% Wilson interval of [0.894, 0.9694]. The target failed on test in
  seeds 2 (0.9032) and 3 (0.8387). The generator was **not** tuned to
  make the target pass.
- **Baselines (synthetic scenario set):** mean pooling ties AlertLens on
  recall (0.9419 ± 0.0803) and beats it on precision (0.7256 ± 0.1108,
  reduction 73.55% ± 3.21%), failing the target in seeds 0 and 3 — under
  overlapping flows the pooling choice is a wash on recall and mean
  pooling is ahead on precision, so noisy-OR is reported as no advantage
  here, not a win. Severity-only still meets recall (1.0000) but at
  precision 0.4937 and only 59.18% reduction — it surfaces roughly half
  the benign incidents too. So the hard set defeats ML-only separation,
  not severity-only recall; severity-only's weakness is precision, not
  recall.
- **Part C: NOT RUN in this build** (no `data/unsw-nb15.csv` shipped).
  The work-copy numbers are in the separate section below and are
  labelled as such; they are not this build's numbers.

## Part C — measured in the work-copy run (NOT the portable build)

In the work copy, where `data/unsw-nb15.csv` (175,341 rows, 119,341
malicious, 45 columns) exists, the 6-feature severity-free model was
re-run (fix pass 3) and Part C measured: the file is split stratified
60/20/20 with fixed seed 42 (train 105,204 / val 35,068 / test 35,069);
features are the real UNSW columns `dur, sbytes, dbytes, rate, sttl,
ct_srv_src` in a saved sklearn Pipeline (imputer + scaler +
GradientBoosting) — no zero-fill, no clipping. The threshold (0.6332) is
calibrated on val (recall 0.9503, target met) and reported on **test
flows only**: recall 0.9486 (95% Wilson [0.9458, 0.9514]), precision
0.9334, reduction 30.83% (fraction of test flows suppressed). The target
was **not met** on test — 22,643 of 23,869 malicious test flows surfaced.
The previous run's 0.9497 / 0.8718 / 25.85% came from the model that
still carried the all-NaN `severity_num` feature and is superseded, not
kept. Part C is flow-level, not incident-level, and is never merged into
the synthetic claims. Citation: Moustafa and Slay (2015), "UNSW-NB15: a
comprehensive data set for network intrusion detection systems", MilCIS
2015. The alert stream for Part C is built by
`scripts/make_alerts_from_unsw.py` (175,341 alerts written to
`data/unsw_alerts.csv`, 119,341 malicious). Note the file has no
`srcip`/`dstip` columns, so `src_ip`/`dst_ip` in that stream are
deterministic placeholder 10.x.y.z addresses hashed from the row id —
identifiers only, never model features.

### Why there are two UNSW thresholds: 0.6332 vs 0.6278

These are two different thresholds for two different purposes, not a
contradiction — verified against the code and the recorded outputs:

- **0.6278** (`models/threshold.json`, validation_recall 0.9501,
  source `unsw-nb15.csv`) is the **saved model's paired threshold**.
  `python scripts/train.py` trains one model on the full UNSW file
  split 80/20 (`test_size=0.2`, `random_state=42`, stratified) and
  calibrates the threshold on that 20% validation split, then writes
  `models/model.pkl` + `models/threshold.json` together.
  `load_model()` reads it only when the saved model actually loads, and
  Part A in the work copy uses it (threshold 0.6278, 6 surfaced,
  2 suppressed, recall 0.75).
- **0.6332** is **Part C's own calibration inside `benchmark.py`**.
  Part C splits the file 60/20/20 (seed 42), trains its own model on
  the 60% train split (105,204 flows), calibrates the threshold on the
  separate 20% val split (35,068 flows, val_recall 0.9503), and reports
  on test flows only. It never writes `models/threshold.json` and is
  never used by Part A or the API.

Different training sets and different validation sets give different
calibrated thresholds; both are recorded as measured. Neither can be
reproduced without the dataset: if `data/unsw-nb15.csv` is absent,
Part C is NOT RUN and `scripts/train.py` falls back to synthetic data
and writes a synthetic threshold instead — so a threshold.json found
without the dataset next to it proves nothing about UNSW-NB15.
